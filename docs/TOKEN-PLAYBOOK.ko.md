# Laya 사내 활용과 토큰 절약 가이드북

판본 1.0 | 2026-10-06 | Windows · 한국어 업무 · Laya 자체 외부 전송 차단

이 가이드 자체는 공개 배포용입니다. 회사가 승인한 Claude·GPT Enterprise 업무 흐름은 유지합니다. 추가 설치하는 Laya는 입력·판정 기준·출력을 별도 외부 서버로 전송하지 않습니다. 실제 회사 자료는 공개 저장소나 승인되지 않은 서비스에 올리지 않습니다.

[인쇄용 PDF](TOKEN-PLAYBOOK.ko.pdf)를 함께 제공합니다.

이 가이드의 목적은 반복되는 분류·선별 업무에서 큰 모델의 호출과 입력량을 줄이는 것입니다. 실행 전에는 같은 배포본의 **SECURITY-STATUS.ko.md와 INSTALL.ko.md**를 확인합니다. 이 문서의 설계 예제는 현재 패키지에 모두 구현된 기능 목록이 아닙니다. 보안 상태가 HOLD이면 실제 업무 자료를 넣지 않고 합성 자료만 사용합니다.

## 1. 먼저 적용할 다섯 가지

1. 모델을 부르기 전에 확장자, 필수 항목, 정확한 코드, 계산을 일반 프로그램으로 처리합니다.
2. 전체 문서 대신 업무 질문에 필요한 후보 문단을 로컬에서 찾습니다.
3. 권한과 버전까지 같은 반복 요청은 승인된 로컬 캐시에서 재사용합니다.
4. 남은 좁은 분류·관련성 판단을 Laya에 맡깁니다.
5. 불명확한 결과는 담당자 검토로 보류합니다. 필요하면 회사가 승인한 Claude·GPT Enterprise 또는 내부 모델로 담당자가 이어서 처리합니다. Laya 패키지가 외부 AI로 자동 전환하지 않습니다.

**우선순위는 호출 제거 → 중복 제거 → 입력 선별 → 좁은 판정 → 필요한 생성입니다.** 처음부터 모든 업무 앞에 Laya를 추가하면 호출·지연·오류가 오히려 늘 수 있습니다.

### 어떤 일을 맡길 수 있습니까?

문의 담당 부서 추천, 문서 유형 태그, 검색된 문단의 관련성 선별, 근거 부족 후보 표시처럼 결과를 쉽게 검토·수정할 수 있는 일부터 시작합니다. 송금, 접근 권한, 계약 승인, 파일 삭제, 사외 전송 허용은 고정 정책과 담당자가 결정합니다. Laya 결과가 해당 행동의 실행 권한을 만들지 않습니다.

Laya는 선택지·점수·예/아니오를 내는 판정 모델입니다. 긴 보고서 작성이나 복잡한 추론을 대신하는 범용 생성 모델이 아닙니다. 현재 고정 모델은 Laya Multilingual이며, 한국어 업무별 검증을 거쳐야 합니다.[1][2]

## 2. 토큰·비용·보안을 따로 측정합니다

절약하려는 대상을 먼저 정합니다. 큰 모델의 토큰, Laya가 읽는 토큰, 지연, 전력, 검토 인력은 서로 다른 지표입니다.

| 지표 | 의미 | 기록 방법 |
| --- | --- | --- |
| 큰 모델 입력·출력 토큰 | 기존 생성 모델이 실제 처리한 양 | 같은 모델·토크나이저로 전후 비교 |
| Laya 처리량 | 판정 입력과 질문·선택지의 처리량 | 전체 조합과 모델 버전을 함께 기록 |
| 승인된 서비스의 사용량 | Claude·GPT Enterprise 등 기존 서비스의 처리량 | 실제 계약·사용량 자료로 별도 확인 |
| 업무당 총비용 | 연산·전력·검토·오류 복구·운영 비용 | 실패·재시도·보류를 포함 |
| 품질 | 최종 정답·중요 근거 누락·보류 | 고정된 독립 평가 집합으로 비교 |

한국어 글자 수나 UTF-8 바이트를 일정 비율로 나눠 실제 토큰이라고 기록하지 않습니다. 모델마다 토크나이저가 다릅니다. 필요한 질문·기준·구분자와 사용 중인 생성 모델의 채팅 형식까지 포함합니다. 청구 자료가 없으면 비용을 추정값으로 구분합니다.

**배치 처리**는 같은 입력의 논리적 토큰 수를 자동으로 줄이지 않습니다. 보통 처리량과 호출 오버헤드를 바꿉니다. **프롬프트 캐시**는 재사용된 입력의 가격이나 연산을 줄일 수 있지만 요청에 포함된 논리적 토큰 수와 같은 개념이 아닙니다. **판정 결과 캐시**는 동일 요청의 추론 자체를 생략합니다.

## 3. 실전 레시피 A: 규칙으로 호출을 없앱니다

예를 들어 문의 접수에는 모델 호출 전에 다음 순서로 검사합니다.

1. 입력이 비었거나 필수 첨부가 없으면 추가 정보를 요청합니다.
2. 확정된 티켓 유형 코드가 있으면 회사의 버전 고정 매핑을 사용합니다.
3. 같은 티켓의 중복 제출이면 기존 처리 결과를 찾습니다.
4. 의미를 해석해야 하는 요청만 분류 후보로 보냅니다.

안전한 규칙은 명확하고 검증 가능합니다. `문자열에 환불이 있으면 billing` 같은 규칙은 “환불 문제가 아닙니다”를 잘못 처리합니다. 키워드는 후보 검색에 쓰고, 최종 의미 분류와 구분합니다. 규칙으로 처리한 건수와 규칙 오류도 평가에 포함합니다.

**작업 기록 예:** 전체 1,000건 중 필수 항목 부족 80건, 정확한 유형 코드 170건이면 모델 진입 후보는 750건입니다. 이 숫자는 계산 설명용 가정입니다. 실제 업무에서 모델이 250건 줄었다고 보고하려면 접수 기록으로 확인해야 합니다.

## 4. 실전 레시피 B: 필요한 문단만 읽힙니다

문서 검색은 제목·문서 ID·버전·섹션·정확한 용어로 후보를 찾은 뒤 문단 단위로 좁힙니다. 첫 도입에서는 로컬 문자열 검색이나 BM25처럼 설명하기 쉬운 기준선을 둡니다. 로컬 임베딩 검색을 추가한다면 임베딩과 인덱스도 회사 데이터로 관리합니다.

### 줄이기 전과 후

줄이기 전에는 업무 매뉴얼 전체와 지난 대화 전체를 큰 모델에 반복 전달합니다. 줄인 뒤에는 질문, 현재 적용되는 규정의 식별자, 관련 문단과 예외·정의·표 머리글, 원문 위치만 전달합니다. 원문은 내부에서 다시 열 수 있어야 합니다.

아래 내용은 압축 과정에서 보존합니다.

- 부정: “환불 대상이 아닙니다.”
- 시점: “오류는 해결됐고 현재는 결제 금액을 확인합니다.”
- 숫자와 단위: 15일, 15영업일, 15만원은 다릅니다.
- 예외와 범위: 특정 계약·지역·시행일에만 적용되는 조건.
- 표의 제목·행/열 관계, 각주와 참조 조항.

처음부터 top-k를 작은 값으로 고정하지 않습니다. 평가 자료에서 정답 근거가 후보에 포함되는 비율을 측정한 뒤 조정합니다. 근거가 없으면 내부 재검색이나 사람 검토로 돌립니다. Laya가 관련 없다고 답했다는 이유만으로 중요 문서를 영구 배제하지 않습니다.

청크 크기와 겹침은 입력 특성에 맞춥니다. 작은 청크는 호출 수와 중복 질문을 늘리고, 큰 청크는 관련 없는 내용을 늘립니다. 겹치는 문단의 중복 비용도 집계합니다. 길이를 초과하면 조용히 자르지 말고 나누거나 보류합니다.

## 5. 실전 레시피 C: 정확한 결과 캐시

캐시는 동일한 자료에 같은 판정을 반복할 때 가장 직접적으로 호출을 줄입니다. 다음 항목을 모두 캐시 키의 범위에 포함합니다.

```text
보안 구역 + 사용자/문서 접근 권한 범위
+ 모델 파일 해시 + 런타임/전처리 버전
+ 질문 + 분류 기준 + 선택지 내용과 순서
+ 원문 내용 또는 변경을 정확히 반영하는 버전
+ 후처리/보류 정책 버전
```

공백이나 문장부호를 임의로 제거하지 않습니다. 코드, 표, 숫자 형식이나 문서 구조에서는 의미가 달라질 수 있습니다. 처음에는 원문이 완전히 같은 요청만 재사용하는 방식이 관리하기 쉽습니다. 유사 문장을 같은 결과로 처리하는 의미 캐시는 별도의 오답·권한 평가를 거쳐야 합니다.

짧은 원문의 SHA-256은 익명화가 아닙니다. 추측 가능한 값을 대조할 수 있습니다. 필요하면 회사 내부 키로 HMAC을 사용하고 키·캐시 값의 접근 권한, 암호화, 보존 기간을 정합니다. HMAC만으로 캐시 값이 암호화되거나 접근 통제가 생기는 것은 아닙니다.

정책·모델·권한이 바뀌면 이전 결과의 재사용을 중단합니다. 삭제 대상은 회사의 복원 가능한 휴지통 절차에 따릅니다. 자동 영구 삭제 예제를 배포하지 않습니다. 회사 정책상 캐시를 허용하지 않으면 캐시를 사용하지 않습니다.

## 6. 실전 레시피 D: 작고 명확한 판정 질문

한 질문에는 한 업무 판단을 담고 선택지의 의미를 구별합니다. 입력 부족과 정상적인 범위 밖을 별도 처리합니다.

```json
{
  "question": "현재 문의를 담당할 부서를 고르십시오.",
  "choices": {
    "billing": "결제 금액, 청구, 중복 결제, 환불",
    "technical": "현재 발생 중인 오류나 접속 장애",
    "sales": "구매 전 가격, 견적, 신규 도입",
    "other": "내용은 있지만 위 유형에 해당하지 않음",
    "unknown": "문의 내용이나 판단 근거가 부족함"
  }
}
```

위 JSON은 질문 설계 예시이며 현재 실행기의 입력 스키마가 아닙니다. 실제 인터페이스는 해당 배포본의 설치 안내를 따릅니다. 업무 요청을 받지 않는 검증판의 제한을 우회해 실행하지 않습니다.

짧은 영문 라벨을 쓰더라도 한국어 설명을 유지합니다. 한국어를 영어로 자동 번역하면 번역 연산, 의미 손실, 검토 비용이 생깁니다. 토큰만 줄었다고 성공으로 판단하지 않습니다. Laya 패키지에 외부 번역 API 호출을 추가하지 않습니다. 별도 번역 서비스 사용은 회사가 승인한 범위로 제한합니다.

선택지가 많으면 계층 분류를 실험할 수 있습니다. 다만 첫 분류 오류가 다음 단계로 전파되고 총 호출 수가 늘어납니다. 평면 분류와 동일한 평가 자료로 비교합니다. 모든 판단을 여러 개의 예/아니오 질문으로 바꾸는 방법도 질문 반복 비용을 확인해야 합니다.

## 7. 실전 레시피 E: 출력·재시도·모델 로딩

큰 모델에게 필요한 결과가 라벨 하나라면 설명문 전체를 요구하지 않습니다. 가능한 경우 짧은 구조화 결과와 필요한 근거 위치만 받습니다. 긴 사고 과정을 출력하게 하는 방식은 토큰 절약 수단이 아닙니다.

형식 검사에 실패하면 무제한 재시도하지 않습니다. 결정적인 스키마 검사를 먼저 하고, 허용된 한도 안에서만 재시도한 뒤 보류합니다. 재시도 입력·출력과 실패도 비용에 포함합니다. Laya에서 외부 모델로 자동 전환하는 복구 경로는 만들지 않습니다. 기존 Enterprise 도구로 이어지는 업무는 회사의 승인된 절차로 처리합니다.

반복 추론에서는 모델을 매번 로딩하는 시간을 측정합니다. 지속 실행·배치는 처리 시간을 줄일 수 있지만 메모리, 접근 권한, 프로세스 수명과 네트워크 표면을 함께 설계해야 합니다. 이 가이드가 현재 패키지에 상시 서버를 제공한다는 뜻은 아닙니다.

## 8. 계산 예제와 로컬 계산기

다음은 **성능 측정이 아닌 가정 기반 예제**입니다. 큰 모델은 회사가 승인한 Claude·GPT Enterprise 또는 내부 모델입니다. Enterprise 요금제의 실제 비용·한도·캐시 할인은 계약과 사용량 자료로 확인하며, 이 계산기는 큰 모델 처리 토큰만 비교합니다.

| 단계 | 가정 | 남은 요청 |
| --- | --- | --- |
| 시작 | 전체 1,000건 | 1,000 |
| 규칙 처리 | 250건 처리 | 750 |
| 정확한 캐시 | 남은 요청의 40%, 300건 적중 | 450 |
| Laya로 완료 | 캐시 미적중의 80%, 360건 완료 | 90 |
| 승인된 큰 모델 | 90건만 생성·심층 처리 | 90 |

기존에 매 건 큰 모델 입력 1,200 + 출력 120토큰이면 합계는 1,320,000토큰입니다. 후보에서는 90건에 입력 350 + 출력 80토큰을 사용해 38,700토큰이 됩니다. **큰 모델 처리 토큰은 약 97.07% 감소**합니다. 이는 이 가정의 산술 결과이며 Laya의 실제 절감 성능이 아닙니다.

Laya 450건의 연산과 질문 처리, 검색·캐시 관리, 품질 검사, 사람 검토 비용은 별도로 더합니다. 같은 토큰 수라도 모델별 비용과 연산량은 다릅니다. 규칙·캐시·Laya의 처리율을 모두 전체 건수에 곱해서 중복 계산하지 않습니다. 위 표처럼 각 단계의 남은 요청을 기준으로 계산합니다.

**반대로 늘어나는 예제도 있습니다.** 기존 1,000건에 입력 200 + 출력 30토큰을 썼고 규칙·캐시 효과가 없다고 가정합니다. Laya가 10%만 끝내고 나머지 900건에 늘어난 지시문 때문에 입력 250 + 출력 30토큰을 쓰면, 큰 모델 토큰은 230,000에서 252,000으로 **약 9.57% 증가**합니다. 여기에 Laya 연산까지 추가됩니다. 두 예제 모두 가정이며, 실제 도입에서는 단계별 비교로 효과를 분리합니다.

첫 예제에서 다른 조건을 유지하면 큰 모델 토큰은 규칙 적용 뒤 990,000, 캐시까지 적용 뒤 594,000, Laya까지 적용 뒤 118,800, 큰 모델 입력·출력까지 줄인 뒤 38,700입니다. 이 분해는 어느 조치가 효과를 냈는지 보여 줍니다. 각 단계의 품질이 같다는 보장은 별도로 시험해야 합니다.

공개 합성 숫자만 포함한 예제를 로컬에서 실행할 수 있습니다. 저장소 루트에서 실행합니다.

```text
python -B tools/token_budget.py examples/token-budget.synthetic.json
python -B tools/token_budget.py --self-test
```

이 계산기는 Python 표준 라이브러리로 숫자만 읽으며 네트워크 호출, 모델 실행, 원문 수집을 하지 않습니다. 입력은 UTF-8 JSON입니다. 기본 출력은 화면이며, 파일로 저장하면 그 파일도 회사의 관리 대상입니다. 입력 수치는 실제 계측값과 가정값을 구분해 기록합니다.

## 9. 절약보다 먼저 확인할 품질

현재 보존된 초기 합성 시험은 12건 중 7건 정답입니다. “앱 오류는 해결됐고 현재 결제 문제”라는 입력을 기술 문의로 잘못 분류하면서 answer_confidence가 약 0.9089였습니다. 높은 확신은 정답 보장이 아닙니다. 이 12건으로 업무 임계값을 정하지 않습니다.

평가 집합은 학습·프롬프트 조정·확률 보정에 쓰는 자료와 분리합니다. 같은 문서의 유사본이 양쪽에 들어가지 않게 합니다. 실제 회사 자료가 필요한 Laya 평가는 회사가 승인한 PC에서 Laya 자체의 외부 전송 차단을 확인한 뒤 수행합니다. 기존 Enterprise 도구를 함께 평가할 때는 회사의 이용 정책을 따릅니다.

최소한 부정문, 과거 문제와 현재 문제, 수치·단위, 오탈자, 한영 혼용, 사내 약어, 내용 없는 요청, 없는 첨부, 선택지 순서 변경, 긴 입력 끝의 핵심 근거를 포함합니다. 업무별 실패 영향을 기준으로 허용 오류율과 근거 누락 한도를 정합니다.

```text
큰 모델 토큰 감소율 = 1 - 후보 토큰 / 기준 토큰
자동처리율 = 자동 확정 건수 / 전체 접수 건수
자동처리 정확도 = 자동 확정 중 정답 / 자동 확정 건수
근거 포함률 = 정답 근거가 검색 후보에 포함된 건수 / 평가 대상 건수
최종 업무 성공률 = 사람 검토까지 포함한 최종 성공 / 전체 시도
```

분모가 0인 비율은 N/A입니다. 보류를 제외한 높은 정확도만 제시하지 않습니다. 보류율, 검토 시간, 실패·재시도, 심각한 누락을 함께 기록합니다. 기준선과 후보는 같은 자료·모델 버전·처리 조건을 유지하고 한 번에 한 조건씩 바꿉니다.

## 10. Laya 자체의 외부 전송을 막습니다

회사에서 승인한 Claude·GPT Enterprise 사용은 기존 업무 흐름으로 유지합니다. 이 패키지의 보안 범위는 **Laya 프로세스가 입력·판정 기준·결과를 별도 외부 서버로 보내지 않게 하는 것**입니다. PC 전체 인터넷 차단이나 가상 머신 설치를 기본 필수 조건으로 두지 않습니다. Enterprise의 보관·학습·커넥터 정책은 회사 계약과 설정을 따릅니다.

아래 세 단계는 회사 자료를 넣기 전에 충족해야 하는 배포 조건입니다. 현재 구현에서 검증이 끝난 항목은 이 절 끝의 현재 상태에 따로 적습니다.

**반입 단계:** 사내 자료가 없는 준비 환경에서 고정된 공개 코드·모델·의존성을 받습니다. 출처, 해시, 라이선스와 허용 목록을 확인합니다. 버전 변경 시 별도 검증합니다. 설치에 필요한 공개 파일 다운로드와 실제 업무 입력을 처리하는 실행 단계를 분리합니다.

**실행 단계:** Laya는 준비된 로컬 모델만 읽어야 합니다. 실행 중 모델 다운로드, 텔레메트리, 원격 오류 수집, 외부 API 전환이 없어야 합니다. 모델 누락·해시 불일치·필수 실행 보호 실패는 오류로 종료해야 하며, 다운로드하거나 다른 모델로 바꿔 작업을 계속하지 않아야 합니다.

**결과 단계:** Laya 결과와 캐시는 회사가 승인한 저장 위치에 둡니다. 공개 GitHub, 개인 클라우드 동기화 폴더, 승인되지 않은 진단 서비스로 보내지 않습니다. 담당자가 결과를 기존 Enterprise 업무에 활용할 때는 해당 회사 정책을 따릅니다.

설계는 오프라인 환경 변수와 Python 네트워크 훅에 더해 전용 실행기의 AppContainer·자식 프로세스 제한을 사용합니다.

**현재 상태:** 소스에는 업무 입력 차단, 실행 중 다운로드 경로 없음, 모델·설치 파일 해시 검사가 들어 있습니다. 변경된 실행기의 빌드, AppContainer 통합 검증, 변경 소스의 로컬 추론 검증은 완료되지 않았습니다. 기존 런타임은 `-S`를 지정해도 `site`를 로드하는 것이 관찰돼 새 설치 검증을 통과하지 못합니다. 따라서 현재 패키지는 공개 합성 자료 전용이며 업무 입력 인터페이스도 제공하지 않습니다. 세부 검증 상태는 같은 배포본의 SECURITY-STATUS.ko.md를 확인합니다. AppContainer capability 0 설정은 통신 경계의 한 요소이며, 패키지와 무관한 다른 프로그램의 전송까지 제어하지는 않습니다.[3]

### 설치본에서 확인할 항목

- 자동 다운로드, 텔레메트리, 원격 오류 수집과 외부 API 호출이 비활성화돼 있는지 확인합니다.
- 로컬 모델만 로드하고 파일 누락·변조 시 종료하는지 확인합니다.
- 합성 입력의 정상 추론과 명시적인 네트워크 시도 차단을 각각 시험합니다.
- Python과 네이티브 네트워크 경로, 자식 프로세스 제한 결과를 구분해 기록합니다.
- 업데이트 후에는 변경된 파일·의존성과 관련 검사를 다시 확인합니다.
- 기존 Enterprise 프로그램의 동작과 Laya의 별도 외부 통신을 혼동하지 않습니다.

통신 시험에는 합성 표식만 사용합니다. 실제 사내 자료를 시험 패킷이나 외부 코드 검토 서비스에 보내지 않습니다. 회사에 더 엄격한 격리 정책이 있으면 그 정책을 적용합니다. Laya 통신을 허용하거나 외부 fallback을 추가해 실행 오류를 해결하지 않습니다.

## 11. 공개 GitHub에 넣을 것과 넣지 않을 것

공개 대상은 프로그램 소스, 설치 안내, 이 가이드, 공개 합성 예제, 버전·SHA-256, 라이선스와 필요한 고지입니다. 계정은 sukwoo0711-maker이고 저장소 이름은 laya-local-decisions입니다. 실제 게시 여부와 배포 버전은 저장소 및 Release에서 확인합니다.

회사 원문·판정 기준·출력·캐시·개발 로그·API 키·개인 경로·비공개 평가 자료는 공개하지 않습니다. `.gitignore`만 믿지 않고 실제 커밋 파일 목록과 배포 압축파일의 내부 목록을 검사합니다. 압축파일도 같은 공개 기준을 적용합니다.

모델 가중치와 설치 런타임은 일반 Git에 넣지 않습니다. GitHub만 접근할 수 있는 회사에는 검증된 Release 묶음 또는 승인된 내부 저장소가 필요합니다. 모든 의존성의 라이선스·고지·재배포 조건을 확인한 뒤 묶습니다. 해시는 신뢰할 수 있는 기준 목록과 대조해야 의미가 있습니다.[4]

**다운로드가 가능하다는 사실은 회사 반입 승인이나 사내 환경의 검증 완료를 뜻하지 않습니다.** 공개 패키지의 상태와 회사 PC의 인수 결과를 각각 기록합니다.

### 실행 전 1분 점검

사용 중인 패키지 버전과 보안 상태를 확인합니다. 입력·결과 폴더가 개인 클라우드 동기화 경로가 아닌지 확인합니다. 자동 다운로드·외부 API·원격 로그가 없는지 확인합니다. Laya 전용 실행 경로가 통신 차단 검사를 통과했는지 확인합니다. 불명확한 입력이 담당자 검토로 가는지 합성 예제로 확인합니다.

## 13. 사례에서 가져올 노하우

공개 구현은 아이디어의 출처이며 그대로 사내에 설치할 승인 근거가 아닙니다. 자세한 출처·과거 관측·한국어 모델 비교는 기존 GUIDE.ko.md에 보존합니다.

- **jgrep:** 먼저 문자열 검색으로 후보를 줄이고 청크·캐시를 사용합니다. 이 설계를 참고할 수 있지만 원본의 외부 Jev 호출은 사내 구성에 가져오지 않습니다.[5]
- **Laya 공식 구현:** 좁은 typed decision, 고정 모델과 확률 보정의 구분을 배웁니다. 공개 벤치마크를 회사 업무 정확도로 대체하지 않습니다.[1][2]
- **한국어 laya-ko:** 과제별 튜닝과 한국어 평가의 필요성을 보여 주는 후속 검토 후보입니다. 저자 성능 수치는 자체 재현 결과와 구분하며 데이터 라이선스를 별도 확인합니다.[6]
- **로컬 도구 전반:** localhost 서버, 로컬 모델, 로컬 캐시라는 이름만으로 전체 흐름이 내부에 머무는 것은 아닙니다. teacher, fallback, 원격 진단과 업데이트 경로를 확인합니다.

이 가이드의 계산 예제는 합성 가정입니다. 실제 토큰 절감률은 회사의 같은 업무 집합에서 측정한 뒤 기록합니다. 모델명, 짧은 소개 글, 커뮤니티 작성자의 경험만으로 품질이나 경제성을 확정하지 않습니다.
